# Product-Development Conference Gates

One monolithic meeting is not a reliable way to design a complex product. The runtime therefore holds persistent linked conferences at each artifact gate.

| Gate | Primary artifact | Mandatory review themes | Exit evidence |
|---|---|---|---|
| G0 Problem | customer problem and baseline | product, applications, market, finance | repeated costly workflow and measurable baseline |
| G1 Requirements | requirement/traceability baseline | systems, product, test, safety, security | measurable SHALL statements and verification methods |
| G2 Architecture | system architecture and ICDs | every affected technical domain, manufacturing, test | budgets, interfaces, alternatives, risks and simulations |
| G3 Detailed design | schematic/CAD/code/model/process artifacts | domain specialists and interface owners | calculations, reviews, static checks, prototypes as required |
| G4 Bring-up | controlled bring-up plan | electrical, firmware, instrumentation, safety | expected checkpoints, limits, recovery and captured evidence |
| G5 Verification | requirement verification matrix | test, metrology, reliability, security/regulatory as applicable | representative pass/fail evidence and deviations |
| G6 Production | released configuration and process | NPI, manufacturing, quality, supply, service | process capability, test coverage, genealogy and release approval |
| G7 Field learning | telemetry/support/failure evidence | product, applications, reliability, data, finance | measured value, failure trends and controlled product updates |

Each sub-conference publishes an artifact and unresolved-risk interface to the system-level integration conference. This preserves detail without exceeding any one model context window.
