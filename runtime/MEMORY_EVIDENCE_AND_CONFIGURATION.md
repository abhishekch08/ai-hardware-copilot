# Memory, Evidence and Configuration Architecture

## Why this matters

The Lab Copilot cannot become reliable if its memory is a bag of chat transcripts. Hardware engineering depends on **configuration identity, measurement provenance, causal evidence and revision control**.

This document defines what the agent organization should remember and how.

---

## 1. Four distinct memory types

### A. Product truth
Validated facts intended to remain true across sessions:

- system architecture;
- requirements;
- approved interfaces;
- validated component properties under stated conditions;
- released limits;
- accepted decisions.

### B. Configuration truth
Identity of the exact thing being discussed:

- PCB revision;
- assembly variant;
- BOM revision;
- serial number;
- firmware commit/build;
- FPGA bitstream;
- desktop/mobile/backend version;
- model/prompt/tool version;
- fixture revision;
- mechanical revision;
- calibration version.

### C. Evidence memory
Raw and processed observations:

- scope traces;
- screenshots/images/video;
- DMM/SMU/PSU readings;
- logic/protocol traces;
- logs;
- test reports;
- simulation outputs;
- thermal/RF/optical/acoustic datasets;
- customer evidence;
- benchmark results.

### D. Reasoning artifacts
Auditable summaries of why a conclusion was reached:

- assumptions;
- hypothesis tables;
- calculations/equations;
- alternative designs;
- experiment predictions;
- decision records;
- reviewer findings;
- verification status.

Do not store hidden model chain-of-thought. Persist the structured artifacts needed to reproduce the engineering decision.

## 5. Decision object

Use `schemas/DECISION_RECORD_TEMPLATE.md`, with links to evidence and affected requirements/configurations.

A durable decision should contain:

- problem;
- constraints;
- considered alternatives;
- trade matrix;
- evidence;
- rejected alternatives and why;
- accepted choice;
- residual risk;
- validation plan;
- triggers for revisiting the decision.

---

## 6. Knowledge status labels

Use explicit epistemic states:

- `CLAIM` — stated but not yet checked;
- `ASSUMPTION` — deliberately adopted for analysis;
- `CALCULATED` — supported by explicit calculation;
- `SIMULATED` — generated by a stated model;
- `MEASURED` — direct observation with acquisition context;
- `REPRODUCED` — independently repeated;
- `VERIFIED` — satisfies defined verification criteria;
- `RELEASED` — accepted into product baseline;
- `INVALIDATED` — evidence shows it is wrong;
- `OBSOLETE` — true for an older configuration only.

---

## 7. Golden-unit memory

Golden units are useful only when configuration and statistical variation are explicit.

Store:

- unit identity;
- why it qualifies as golden;
- build/rework history;
- firmware/configuration;
- baseline traces;
- expected ranges rather than only single traces;
- environmental conditions;
- aging history if relevant.

The agent should compare against both **specification** and **golden population**, because a golden unit can itself contain a latent design flaw.

---

## 8. Source provenance

Every external technical assertion should retain:

- source title/URL/file;
- revision/date;
- exact section/table/page when practical;
- retrieval date for mutable web sources;
- whether source is primary, secondary or anecdotal.

A distributor summary should not silently override the manufacturer's datasheet. A datasheet typical value should not become a guaranteed production limit.

---

## 9. Data separation

Keep these logically separated:

```text
RAW EVIDENCE
    -> immutable
DERIVED FEATURES
    -> regenerable from raw evidence
INTERPRETATION
    -> model/agent-version dependent
DECISION
    -> human/company artifact with rationale
```

When an algorithm changes, recompute derived features without modifying raw measurements.

---

## 10. Agent/model version provenance

For every significant AI-generated artifact record:

- agent ID/version;
- model/provider/version when available;
- prompt/constitution version;
- tool versions;
- retrieval corpus version;
- reviewers;
- evaluation status.

This allows regression analysis when a model or prompt changes behavior.

---

## 11. Retrieval rules

When building task context:

1. prioritize same exact configuration;
2. then same revision/family;
3. then validated generic product knowledge;
4. then external engineering knowledge.

Older-revision evidence must be labeled clearly.

---

## 12. Memory hygiene

Agents should periodically identify:

- conflicting facts;
- obsolete revision knowledge;
- orphaned measurements;
- decisions without verification;
- failed hypotheses mistakenly referenced as facts;
- unsupported numeric limits;
- duplicated datasets;
- stale model benchmarks.

The objective is **traceable engineering memory**, not maximal retention.
